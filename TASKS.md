## Resolved — Twilio delivery-status + inbound webhooks, Text Activity tab
Built 2026-08-28. Two real bugs found and fixed along the way, both live since the SMS feature originally shipped:

1. **`client_activity.ref_id` was `uuid`, but Twilio message SIDs (`SM...`) aren't valid UUIDs** — every SMS send's activity-log insert with a `clientId` was silently failing (confirmed: zero `activity_type='sms'` rows existed in prod despite real sends going out). Fixed by widening the column to `text` ([migration](supabase/migrations/20260828220000_client_activity_sms_direction_and_ref_id_fix.sql)) — no constraint/FK depended on it being uuid.
2. **A second migration silently reverted the `sms`/`crew_note` activity_type CHECK values.** [20260815032057_sms_sequence_steps.sql](supabase/migrations/20260815032057_sms_sequence_steps.sql) added `sms`/`crew_note` to `client_activity.activity_type`'s CHECK constraint; a *later* migration ([20260824111010_client_activity_ticket_job_types.sql](supabase/migrations/20260824111010_client_activity_ticket_job_types.sql), written by a different concurrent session from a stale baseline) did its own DROP+ADD CONSTRAINT with only the original values plus `ticket`/`job`, silently dropping `sms`/`crew_note` again on both prod and test. This compounded bug #1 — even after fixing `ref_id`, every SMS insert was *still* failing until [20260828230000_restore_sms_activity_type.sql](supabase/migrations/20260828230000_restore_sms_activity_type.sql) restored the full superset. Same class of drift as other CHECK-constraint collisions in this repo's history: two migrations doing DROP+ADD on the same named constraint without either one being aware of the other's additions — always inspect the CURRENT live constraint on prod before writing a new one, and treat "build the new list as a superset" as literal, not just for the immediate feature.

With both fixed: [`/api/webhooks/twilio/status`](src/app/api/webhooks/twilio/status/route.ts) updates a text's real delivery status (`delivered_at`/`failed_at`, matched by `ref_id`); [`/api/webhooks/twilio/inbound`](src/app/api/webhooks/twilio/inbound/route.ts) logs inbound replies (matched to a client by phone number) and applies opt-out/opt-in keywords to `clients.sms_opt_in` as a backstop to Twilio's own Advanced Opt-Out handling. Both verify `X-Twilio-Signature` via a hand-rolled HMAC-SHA1 check ([verify-twilio-request.ts](src/lib/sms/verify-twilio-request.ts), self-tested against Twilio's own documented test vector — no `twilio` SDK dependency added for one algorithm). `sendClientSms` now passes `StatusCallback` on every outbound send.

The Email Activity page is now "Message Activity" with Email/Text tabs ([page.tsx](src/app/\(crm\)/crm/communication/email/page.tsx), new [SmsActivityList.tsx](src/components/crm/email-activity/SmsActivityList.tsx)) — Sent/Delivered/Failed/Received stat cards, direction icons, status pills. Verified live end-to-end on the test project (inserted a real-shaped row, confirmed the Text tab renders it, deleted after).

**Setup step outside this codebase** (same pattern as the Resend webhook): in the Twilio Console, set the Messaging Service's inbound-webhook URL to `<site-url>/api/webhooks/twilio/inbound` (Request URL, HTTP POST) so Twilio actually calls it — nothing currently does without this.

## In progress — QuickBooks one-way sync
Decided 2026-08-25, scoped in phases. Phase 1 (OAuth2 connection, `src/lib/integrations/quickbooks.ts` + `/api/integrations/quickbooks/*`), Phase 2 (client ↔ QBO customer matching, `/api/crm/clients/[clientId]/quickbooks-sync`), Phase 3 (invoice/payment push), and Phase 4 (reconciliation UI) are built — this is now feature-complete for the originally scoped 4 phases, pending real-credential verification. Matching policy, decided with the user: an exact `DisplayName` match auto-links (safe — QuickBooks enforces DisplayName uniqueness, so an exact match can only ever be 0 or 1 row); zero matches at all auto-creates a new QBO customer; any fuzzy-only match (even a single one) is surfaced for a human to pick rather than guessed. Every client gets its own top-level QBO customer — no sub-customer hierarchy for commercial parent/child clients (deliberately skipped, not in real use yet). No periodic re-verification that a link is still valid — a broken link surfaces the next time a sync against it fails.

**Phase 3 (invoice/payment push), decided with the user:**
- Invoices push automatically when sent (email send route and the manual status-dropdown "sent" transition both fire it — fire-and-forget from the client, awaited server-side from the email route). `crm_invoices.qbo_invoice_id` makes the push idempotent.
- Every line item pushes under one catchall QBO Service item ("Services", auto-created against the org's first Income account on first use) — no per-service QBO item mapping. QBO-side reporting won't break down by TwinsOS service type until a later phase adds that.
- Tax and discounts are NOT mapped as separate QBO lines in this phase — only the invoice's line items (post-discount `total_cents` per line) push. The QBO invoice total may not match the TwinsOS total when tax/discounts apply; needs revisiting before this is relied on for books-of-record accuracy.
- Payments push automatically when recorded, one QBO Payment per `crm_payment_allocations` row (a split payment becomes multiple QBO Payments) — `qbo_payment_id` lives on the allocation row, not `crm_payments`, for that reason. An allocation whose invoice hasn't been pushed to QBO yet is skipped (not force-pushed) — surfaces in Phase 4's reconciliation UI. Prepayments/credits with no invoice allocation are out of scope for this phase.
- Editing an existing payment's allocations (`useUpdatePayment`) does not re-sync or reconcile against QuickBooks — out of scope for this phase.

**Phase 4 (reconciliation + error surface UI), decided with the user:** built. `crm_invoices.qbo_sync_error`/`qbo_sync_attempted_at` and `crm_payment_allocations.qbo_sync_error`/`qbo_sync_attempted_at` (new columns — `integrations.last_sync_status` is org-wide only and can't say which record failed or why). Push functions record the error message on failure, clear it on success. A "Sync Status" panel lives in Settings > Accounting right under the QuickBooks connect section (`GET /api/integrations/quickbooks/sync-status`) — lists every invoice/payment allocation with a recorded error and a per-row Retry button (reuses the existing push routes, which are already idempotent). No auto-retry-forever — retries are manual only.

**Phase 5 (tax/discount lines + per-service item mapping), decided with the user: both.** Built.
- Invoice discounts push as a single `DiscountLineDetail` line (QBO applies it against its own default discount account — no account mapping exists in TwinsOS to point it anywhere more specific).
- Invoice tax pushes as a manual `TxnTaxDetail.TotalTax`. **Unverified against a real QuickBooks company** — a company with Automated Sales Tax enabled computes tax itself per-line via `TaxCodeRef` and will likely reject a manually-set total. Not silent if it does: the failure surfaces through the normal error path into the Phase 4 reconciliation panel with QuickBooks' own error text, so it'll be visible and retryable once diagnosed — but the tax mapping itself may need rework once tested against a real company.
- `crm_services.qbo_item_id` — an invoice line whose name exactly matches (case-insensitive) one of the org's `crm_services` gets that service's own dedicated QBO Service item (created + cached on first use, same "name uniqueness makes an exact match unambiguous" reasoning as client matching). A line with no matching service (ad-hoc/free-text) still falls back to the shared catchall "Services" item — no ambiguous-match UI needed here since Item names are also globally unique in QBO.
